# iQbit 全量中文汉化设计

## 背景

当前项目存在大量未完成的英文用户界面文案，分散在：

- 页面标题与导航
- 按钮、占位符、弹窗操作
- 下载页、搜索页、趋势页、分类页、插件页、集成页
- 设置页中的分组名、字段名、说明文字、下拉选项
- 面向用户展示的状态文本

这些文案目前直接散落在页面和组件中，没有统一的文案组织层，导致继续补齐汉化时需要在项目中到处查找字符串，维护成本高，也容易遗漏。

## 目标

- 完成当前前端所有用户可见文案的中文化
- 不改变现有业务逻辑、接口行为和内部状态判断
- 为后续继续维护文案提供统一入口

## 非目标

- 不引入完整 i18n 框架
- 不实现中英文切换
- 不修改 API 字段、类型名、枚举值、查询键、存储键等内部标识
- 不顺带改写 README、服务端文档或 GitHub 配置文档

## 方案对比

### 方案 A：直接把英文字符串逐个替换成中文

优点：

- 实现最快
- 对现有结构侵入最小

缺点：

- 文案依旧散落
- 后续维护困难
- 容易出现重复文案不一致

### 方案 B：引入轻量文案层，再完成全量中文替换

优点：

- 本次即可完成全站汉化
- 后续维护有统一入口
- 不会把任务膨胀成完整国际化系统改造

缺点：

- 比直接替换多一层整理工作

### 方案 C：直接接入完整 i18n 框架

优点：

- 理论上最完整

缺点：

- 改动面过大
- 会把当前任务扩展为国际化系统重构
- 当前需求只要求完成中文汉化，不需要语言切换

### 推荐方案

采用方案 B。

## 设计

### 文案层

新增一个轻量中文文案模块，例如：

- `src/locales/zh-CN.ts`

该模块集中导出所有用户可见文案，按功能分组，例如：

- 全局通用文案
- 导航与页面标题
- 下载页
- 搜索与趋势
- 分类与插件
- 集成页
- 设置页
- 状态文本

业务组件优先从该文案模块读取显示文本，而不是继续内联散落字符串。

### 内部值与显示值分离

对存在“内部值必须保留英文”的场景，采用“值不改、显示文本改中文”的方式。例如：

- 页面 label 若同时承担路由查找和 UI 展示，则拆出稳定 key 与显示 title
- 设置项 option 若 value 被业务逻辑依赖，则保留原 value，仅把 label 改为中文
- 状态筛选若当前依赖英文状态值进行比较，则额外提供中文显示映射，不直接替换底层值

这样可以避免汉化导致行为回归。

### 覆盖范围

本次会覆盖：

- 导航栏、底部标签、页面标题
- 登录页与认证相关文案
- 下载页中的操作、筛选、表单、弹窗、状态展示
- 搜索页、趋势页、插件页、分类页、标签选择页、字体大小页
- Sonarr/Radarr 集成页
- 设置页中的全部用户可见文案

### 不改动的内容

以下内容保持原样：

- `Sonarr`、`Radarr`、`YTS`、`TMDB`、`qBittorrent` 等专有名词
- 接口字段名、类型名、枚举值、存储键、查询键
- 第三方库返回值和日志行为

## 架构与实现策略

### 页面与组件层

优先改动直接承载 UI 的页面与组件：

- `src/Pages.tsx`
- `src/layout/default.tsx`
- `src/pages/*`
- `src/components/*`
- `src/searchAPIs/*`
- `src/utils/StateDictionary.tsx`

### 设置页

设置页英文文案分散且数量最多，采用以下方式收口：

- 把设置页分组标题、字段标签、helper text、选项文本逐步迁移到文案层
- 保留设置 key 与 option value 的英文内部值
- 仅替换用户可见的 label/title/helperText

### 风险点

1. 某些英文字符串同时承担显示和逻辑判断

处理方式：

- 先识别这些位置
- 必要时拆分为稳定 key 与显示文本

2. 某些下拉选项的英文值是接口约定

处理方式：

- 只翻译显示层 label，不翻译 value

3. 页面间通过英文 page label 查找页面配置

处理方式：

- 若当前 `label` 被同时用于展示和查找，需要改为“内部 key + 中文展示名”的结构

## 验证策略

1. 编译验证

- 运行前端构建，确保没有因为文案层重构导致类型错误或引用错误

2. 重点页面人工回归

- 登录
- 下载页
- 搜索页
- 趋势页
- 分类页
- 插件页
- 集成页
- 设置页

3. 回归重点

- 页面导航仍然正常
- 搜索 provider 切换正常
- 下载页筛选与弹窗操作正常
- 设置项读写逻辑未受影响

## 结论

本次通过“轻量文案层 + 全量中文替换 + 内部值与显示值分离”的方式完成汉化，既能满足当前“全部中文化”的需求，也能避免把任务扩大成完整国际化重构。
